# 3. RELATION PARENT / ÉLÈVE

La règle métier principale est :

```text id="q4t0h4"
1 Élève
    ↓
1 seul Parent / Tuteur principal
```

Et :

```text id="q4t0h5"
1 Parent / Tuteur
    ↓
1 ou plusieurs Élèves
```

Exemple :

```text id="q4t0h6"
Parent : Jean KABILA
    ├── Élève : David KABILA
    ├── Élève : Sarah KABILA
    └── Élève : Grâce KABILA
```

Un élève doit obligatoirement avoir un parent ou tuteur principal selon les règles métier définies pour cette phase.

Un parent peut être associé à plusieurs élèves.

La relation doit être correctement modélisée et validée côté backend.

# 5. RECHERCHE D'UN PARENT EXISTANT

Lors de la création d'un élève, le système doit permettre de rechercher un parent existant avant d'en créer un nouveau.

Flux attendu :

```text id="q4t0h7"
Création d'un élève
        ↓
Recherche d'un parent existant
        ↓
Parent trouvé ?
    ├── Oui
    │    ↓
    │  Sélectionner le parent
    │
    └── Non
         ↓
       Créer un nouveau parent
```

La recherche doit pouvoir utiliser les informations disponibles, notamment :

* nom ;
* prénom ;
* téléphone ;
* email.

La recherche doit être dynamique et limitée à l'école ou au tenant courant.

Un utilisateur ne doit jamais pouvoir sélectionner un parent appartenant à une autre école.

---

# 6. RÈGLE CONTRE LES DOUBLONS DE PARENTS

Avant de créer un nouveau parent, le système doit encourager la recherche d'un parent existant.

Éviter les doublons évidents.

Selon les données disponibles, vérifier notamment :

* téléphone ;
* email ;
* nom ;
* prénom.

Ne pas bloquer abusivement deux personnes qui pourraient réellement avoir les mêmes noms.

Si un doublon potentiel est détecté, afficher une confirmation ou une alerte claire.

Le système doit permettre à l'utilisateur de vérifier si le parent existe déjà avant de créer une nouvelle fiche.

# 8. MATRICULE AUTOMATIQUE

Le matricule de l'élève doit être généré automatiquement par le système.

L'utilisateur ne doit pas saisir manuellement le matricule lors de la création.

Flux attendu :

```text id="q4t0h8"
Création de l'élève
        ↓
Validation des données
        ↓
Génération automatique du matricule
        ↓
Matricule unique
        ↓
Enregistrement de l'élève
```

Le matricule doit être :

* généré côté backend ;
* unique ;
* stable ;
* non modifiable manuellement par l'utilisateur ;
* lié à l'école selon la configuration ;
* protégé contre les doublons.

Le système doit garantir l'unicité même en cas de créations simultanées.

Utiliser les mécanismes appropriés de base de données et de transaction.

---

# 9. FORMAT DU MATRICULE CONFIGURABLE

L'Admin École doit pouvoir configurer le format du matricule selon les besoins de son établissement.

Le système doit permettre une configuration suffisamment flexible.

Exemple :

```text id="q4t0h9"
Préfixe : KLS
Inclure l'année : Oui
Nombre de chiffres : 4
```

Résultat :

```text id="q4t0h10"
KLS-2026-0001
KLS-2026-0002
KLS-2026-0003
```

Autre exemple :

```text id="q4t0h11"
Préfixe : ELV
Année : Non
Nombre de chiffres : 6
```

Résultat :

```text id="q4t0h12"
ELV-000001
ELV-000002
```

La configuration doit pouvoir prévoir, selon l'architecture retenue :

* préfixe ;
* inclusion de l'année ;
* séparateur ;
* nombre de chiffres ;
* numéro de départ ;
* éventuellement un format configurable.

Le format exact doit être défini de manière claire et validée.

---

# 10. RÈGLES DE MATRICULE

Le matricule doit être unique dans le périmètre défini par le projet.

Par défaut, il doit être unique pour une école.

Le système ne doit jamais réutiliser un matricule déjà attribué.

Même si un élève est désactivé ou archivé, son matricule ne doit pas être réattribué à un autre élève.

Le matricule doit rester stable pendant toute la durée de vie de l'élève.

Le matricule ne doit pas dépendre de la classe actuelle de l'élève.

La classe et l'inscription seront gérées dans une phase ultérieure.

---

Exemple de prévisualisation :


Les modifications de configuration ne doivent pas modifier les matricules déjà attribués.

Un changement de configuration doit uniquement affecter les futurs élèves.
