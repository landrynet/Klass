# PROMPT — PHASE 1 : CRÉATION ET CONFIGURATION INITIALE D'UNE ÉCOLE

## CONTEXTE

L'architecture de base de la plateforme **KLASS** a été créée et validée.

Tu dois maintenant développer la **Phase 1 : Fondation d'une école**.

Cette phase doit permettre au Super-Admin de créer une école et à l'Admin École de configurer son établissement avant d'utiliser les autres fonctionnalités du système.

Respecte l'architecture existante et ne réorganise pas inutilement le projet.

Avant toute modification :

1. Inspecte l'architecture actuelle.
2. Vérifie les applications déjà créées.
3. Vérifie la configuration multi-tenant.
4. Vérifie la configuration PostgreSQL.
5. Vérifie le modèle utilisateur existant.
6. Vérifie le système de rôles et permissions.
7. Vérifie les URLs et dashboards existants.
8. Vérifie les migrations existantes.
9. Vérifie les tests existants.
10. Vérifie le `README.md`.
11. Lis `docs/Klass_Document_Projet.docx`.
12. Vérifie la documentation déjà présente dans `docs/`.

Ne détruis pas le travail déjà réalisé.

Si une structure existe déjà, réutilise-la et améliore-la proprement.

---

# 4. CRÉATION D'UNE ÉCOLE PAR LE SUPER-ADMIN

Créer une interface personnalisée KLASS pour le Super-Admin.

**Ne pas utiliser Django Admin.**

Le Super-Admin doit pouvoir créer une école à travers une interface personnalisée.

Le formulaire doit prévoir au minimum :

* nom de l'école ;
* code unique de l'école ;
* adresse ;
* ville ;
* pays ;
* email de contact ;
* téléphone de contact ;
* nom de l'Admin École ;
* email ou identifiant de l'Admin École.

Les informations doivent être validées.

Le code de l'école doit être unique.

Le système doit empêcher la création de doublons.

---

# 5. CRÉATION DU TENANT

Lors de la création d'une école :

```text
Création de l'école
        ↓
Création du tenant
        ↓
Création du schéma PostgreSQL dédié
        ↓
Configuration du domaine ou sous-domaine
        ↓
Création de l'Admin École
```

Le tenant doit être correctement associé à l'école.

Le système doit garantir l'isolation des données.

Une école ne doit jamais pouvoir accéder aux données d'une autre école.

Tester réellement cette isolation.

---

# 6. SOUS-DOMAINE OU DOMAINE DE L'ÉCOLE

Préparer le système pour qu'une école dispose d'une adresse personnalisée.

Exemple :

```text
ecole-a.klass.app
ecole-b.klass.app
```

Le sous-domaine doit permettre d'identifier le tenant courant.

Si l'environnement de développement ne permet pas de créer de vrais sous-domaines, prévoir une configuration de développement documentée permettant de simuler correctement ce fonctionnement.

Le système doit être conçu pour fonctionner avec de vrais sous-domaines en production.

Documenter cette configuration dans la documentation de la Phase 1.

---

# 7. CRÉATION DE L'ADMIN ÉCOLE

Lors de la création d'une école, le système doit créer automatiquement son Admin École.

L'Admin École doit être associé uniquement à son établissement.

Il ne doit pas être un utilisateur global capable d'accéder à toutes les écoles.

Le compte doit avoir le rôle :

```text
school_admin
```

ou le nom de rôle déjà utilisé par l'architecture existante.

Documenter le fonctionnement de ce rôle dans la documentation du module.

---

# 8. IDENTIFIANTS TEMPORAIRES

Lors de la création de l'école :

```text
Login ou email
        +
Mot de passe temporaire
```

doivent être générés ou configurés.

Le mot de passe temporaire doit être sécurisé.

Ne jamais stocker le mot de passe en clair dans la base de données.

Le système doit enregistrer un état indiquant que l'utilisateur doit effectuer sa première configuration.

Exemple :

```text
first_login_required = True
```

ou une logique équivalente adaptée au modèle existant.

Les identifiants temporaires doivent être communiqués de manière sécurisée selon l'architecture prévue.

Documenter le processus dans `docs/`.

---

# 9. PREMIÈRE CONNEXION

Lorsque l'Admin École se connecte pour la première fois, il ne doit pas accéder directement au dashboard normal.

Il doit être redirigé obligatoirement vers le processus de première configuration.

```text
Connexion réussie
        ↓
Vérification première connexion
        ↓
Configuration obligatoire
```

Tant que cette configuration n'est pas terminée :

* l'accès aux autres modules doit être bloqué ;
* l'utilisateur ne doit pas pouvoir contourner l'assistant en modifiant l'URL ;
* les routes sensibles doivent également vérifier cet état côté serveur.

Documenter ce flux dans la documentation du module.

---

# 10. CHANGEMENT OBLIGATOIRE DU MOT DE PASSE

La première étape de la configuration doit obliger l'Admin École à modifier son mot de passe temporaire.

Le nouveau mot de passe doit respecter les règles de sécurité configurées dans le projet.

Après changement réussi :

```text
Mot de passe temporaire
        ↓
Nouveau mot de passe sécurisé
```

Le mot de passe temporaire ne doit plus être utilisable.

---

# 11. INFORMATIONS DE L'ÉCOLE

Créer une étape permettant de compléter ou modifier les informations de l'établissement.

Prévoir notamment :

* nom officiel ;
* logo ;
* adresse ;
* ville ;
* pays ;
* email ;
* téléphone ;
* autres informations nécessaires au fonctionnement de l'école.

Les fichiers doivent utiliser le système de stockage configuré par l'architecture du projet.

Ne pas créer une logique de stockage incompatible avec la configuration existante.

---

# 12. ANNÉE SCOLAIRE INITIALE

L'Admin École doit pouvoir définir l'année scolaire initiale de son établissement.

Exemple :

```text
2026-2027
```

Cette année doit être enregistrée comme année scolaire active.

Préparer proprement l'architecture pour le futur module de gestion des années scolaires.

Ne pas développer encore toute la logique complète de changement d'année scolaire.

---

# 13. ASSISTANT DE CONFIGURATION INITIALE

Créer un assistant de configuration clair et progressif.

Exemple :

```text
Étape 1 — Changement du mot de passe
        ↓
Étape 2 — Informations de l'école
        ↓
Étape 3 — Logo et coordonnées
        ↓
Étape 4 — Année scolaire initiale
        ↓
Étape 5 — Vérification
        ↓
Configuration terminée
```

L'utilisateur doit pouvoir voir clairement :

* l'étape actuelle ;
* les étapes restantes ;
* les erreurs éventuelles ;
* l'état d'avancement.

La configuration doit être enregistrée de manière fiable.

Si l'utilisateur quitte l'assistant avant la fin, il doit pouvoir reprendre la configuration sans perdre les données déjà enregistrées.

---

# 14. CONFIGURATION INITIALE TERMINÉE

À la fin de l'assistant, l'école doit avoir un état clair :

```text
Configuration en cours
        ↓
Configuration validée
        ↓
École opérationnelle
```

L'Admin École ne doit accéder au dashboard complet qu'après validation de la configuration initiale obligatoire.

---

# 15. DASHBOARD PERSONNALISÉ

Créer ou utiliser le dashboard personnalisé de KLASS.

**Ne pas utiliser Django Admin.**

Après la configuration initiale, l'Admin École doit être redirigé vers son dashboard personnalisé.

Le dashboard peut être simple à cette étape.

Il doit au minimum afficher :

* nom de l'école ;
* année scolaire active ;
* état de configuration ;
* accès aux modules disponibles ou à venir.

Les modules non encore développés peuvent apparaître comme indisponibles ou ne pas apparaître selon l'architecture prévue.

---

# 16. SÉCURITÉ ET PERMISSIONS

Vérifier strictement :

* qu'un Admin École ne peut accéder qu'à son propre tenant ;
* qu'un Admin École ne peut pas accéder à une autre école ;
* qu'un utilisateur non autorisé ne peut pas accéder à l'assistant ;
* qu'un utilisateur ne peut pas contourner la première configuration ;
* que les routes sensibles sont protégées côté serveur ;
* que les permissions sont vérifiées à chaque requête importante.

Ne pas se contenter de masquer les boutons dans l'interface.

La sécurité doit être appliquée dans le backend.

---

# 17. GESTION DES ERREURS

Prévoir une gestion propre des erreurs :

* code école déjà existant ;
* tenant déjà existant ;
* erreur de création du schéma ;
* erreur de connexion à la base ;
* erreur de création de l'utilisateur ;
* erreur de sauvegarde des informations ;
* configuration interrompue.

En cas d'erreur lors de la création d'une école, éviter de laisser des données incomplètes ou incohérentes.

Utiliser une logique transactionnelle lorsque cela est possible.

Documenter les erreurs importantes et leurs solutions dans `docs/`.

---

# 18. TESTS OBLIGATOIRES

## Création d'une école

* code unique ;
* prévention des doublons.

## Tenant

* création du tenant ;
* association correcte à l'école ;
* isolation des données.

## Admin École

* création automatique ;
* rôle correct ;
* association au bon tenant.

## Première connexion

* redirection vers la configuration ;
* blocage du dashboard avant configuration ;
* impossibilité de contourner la configuration.

## Mot de passe

* changement obligatoire ;
* ancien mot de passe temporaire invalidé.

## Configuration

* informations de l'école ;
* année scolaire active ;
* validation finale.

## Isolation

Créer au minimum deux écoles de test :

```text
École A
École B
```

Vérifier que :

```text
Admin A ≠ accès aux données de B
Admin B ≠ accès aux données de A
```

Les tests doivent réellement être exécutés et réussir.

Documenter les tests et leurs résultats dans la documentation de la Phase 1.
