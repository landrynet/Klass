# PROMPT — STABILISATION COMPLÈTE DE LA PHASE 1 + PRÉPARATION DE LA PHASE 2

La Phase 1 a été développée.

Tu dois maintenant effectuer une **phase complète de stabilisation, d'audit, de vérification et d'amélioration** avant de commencer le développement fonctionnel de la Phase 2.

L'objectif est de rendre la Phase 1 réellement fiable, cohérente, professionnelle et prête à servir de fondation pour la suite du projet KLASS.

---

# 1. LIRE LA DOCUMENTATION AVANT TOUTE MODIFICATION

Avant de commencer :

1. Lire `docs/Klass_Document_Projet.docx`.
2. Lire toute la documentation présente dans `docs/`.
3. Lire le `README.md`.
4. Vérifier l'état déclaré de la Phase 1.
5. Inspecter toute l'architecture actuelle.
6. Vérifier les fichiers réellement présents dans le projet.

La documentation et le code doivent être comparés.

Si la documentation indique qu'une fonctionnalité existe mais que le code est incomplet, corriger le code ou mettre à jour correctement la documentation.

Ne jamais considérer une fonctionnalité comme terminée simplement parce qu'elle est mentionnée dans un document.

# 3. VÉRIFICATION DE L'INTÉGRITÉ DES FICHIERS

Vérifier que chaque fichier est complet.

Aucun fichier ne doit être :

* coupé ;
* partiellement généré ;
* vide sans raison ;
* dupliqué ;
* incohérent avec son rôle ;
* interrompu au milieu d'une fonction ;
* interrompu au milieu d'une classe ;
* incomplet au niveau HTML, CSS ou JavaScript.

Vérifier particulièrement :

```text
models.py
views.py
forms.py
services.py
permissions.py
urls.py
settings.py
templates
JavaScript
CSS
tests
migrations
```

Corriger les fichiers incomplets.

Ne pas simplement masquer les erreurs.

# 6. VÉRIFICATION DE LA SÉCURITÉ

Tester réellement :

* l'accès sans authentification ;
* l'accès avec un mauvais rôle ;
* l'accès à un autre tenant ;
* l'accès à une autre école ;
* la modification d'un identifiant dans l'URL ;
* l'accès direct aux étapes de l'assistant ;
* le contournement de la première configuration ;
* les accès après déconnexion.

Un utilisateur ne doit jamais pouvoir accéder à des données qui ne lui appartiennent pas.

Les permissions doivent être appliquées côté backend.

Ne jamais se limiter à cacher un bouton dans l'interface.

---

# 7. AMÉLIORATION DE LA PAGE DE CONNEXION

Les pages de connexion doivent être améliorées et avoir un design professionnel.

La page de connexion doit :

* être claire ;
* être moderne ;
* être responsive ;
* être rapide ;
* être accessible ;
* afficher clairement les erreurs ;
* ne pas révéler d'informations sensibles ;
* gérer correctement les mauvaises informations de connexion ;
* permettre une expérience cohérente avec le tenant ou l'école.

Prévoir une identité visuelle cohérente avec KLASS.

La page de connexion doit être pensée comme une véritable interface produit et non comme une simple page technique.

---

# 8. AMÉLIORATION DE L'ASSISTANT DE CONFIGURATION

L'assistant de configuration initiale doit être amélioré afin d'offrir une expérience professionnelle.

Il doit :

* afficher clairement la progression ;
* indiquer l'étape actuelle ;
* indiquer les étapes restantes ;
* permettre de reprendre une configuration interrompue ;
* afficher des messages d'erreur compréhensibles ;
* valider les données correctement ;
* empêcher les étapes incohérentes ;
* éviter la perte de données ;
* gérer correctement les erreurs réseau ;
* fonctionner sur ordinateur et mobile.

L'expérience doit être fluide.

Éviter les formulaires longs et confus.

L'assistant doit guider l'utilisateur de manière progressive.

---

# 10. RESPONSABILITÉ ET ROBUSTESSE DU SYSTÈME

Le système doit être conçu de manière responsable.

Cela signifie notamment :

* ne jamais perdre silencieusement des données ;
* ne jamais supprimer des données sans confirmation appropriée ;
* ne jamais créer de doublons inutilement ;
* ne jamais exposer de mots de passe ;
* ne jamais exposer de données d'un autre tenant ;
* ne jamais ignorer silencieusement une erreur ;
* toujours afficher un état clair à l'utilisateur ;
* gérer correctement les erreurs ;
* prévoir des validations côté client et côté serveur ;
* utiliser des transactions lorsque cela est nécessaire ;
* protéger les opérations sensibles.

Chaque opération importante doit avoir un résultat clair :

```text
Succès
Erreur
En cours
À reprendre
Non autorisé
```
