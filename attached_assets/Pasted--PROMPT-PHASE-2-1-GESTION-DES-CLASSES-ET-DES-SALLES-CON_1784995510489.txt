
# 3. GESTION DES CLASSES

Créer une gestion complète des classes.

Une classe doit être liée à :

* une école ;
* un tenant ;
* une année scolaire ;
* un niveau ;
* une option/filière lorsque cela est applicable ;
* une salle lorsque cela est applicable.

Exemples :

```text
6ème Scientifique A
6ème Scientifique B
5ème Commerciale A
4ème Littéraire A
```

Prévoir au minimum :

* nom de la classe ;
* code éventuel ;
* école ;
* tenant ;
* année scolaire ;
* niveau ;
* option/filière ;
* salle ;
* capacité maximale si nécessaire ;
* statut.

---

# 4. MODÈLE ET RELATIONS DES CLASSES

La structure doit être cohérente avec les phases précédentes :

```text
School
    ↓
AcademicYear
    ↓
Level
    ↓
Track / Option
    ↓
Class
```

Une classe ne doit jamais pouvoir être associée à :

* une année scolaire d'une autre école ;
* un niveau d'une autre école ;
* une option d'une autre école ;
* une salle d'une autre école.

Toutes les relations doivent être vérifiées côté backend.

Ne jamais se limiter à des restrictions dans l'interface.

---

# 5. RÈGLES MÉTIER DES CLASSES

Mettre en place des validations cohérentes.

Une classe doit respecter les relations de son école.

Éviter les doublons incohérents.

Par exemple, selon les règles métier définies par l'architecture :

```text
Même école
+
Même année scolaire
+
Même niveau
+
Même option
+
Même nom
```

ne doit pas créer deux classes identiques.

Les règles doivent être adaptées au modèle réel du projet.

Ne pas imposer une règle qui empêcherait une école de créer plusieurs sections d'un même niveau.

Exemple valide :

```text
6ème Scientifique A
6ème Scientifique B
6ème Scientifique C
```

---

# 6. STATUT DES CLASSES

Prévoir une gestion cohérente des statuts.

Par exemple :

```text
Active
Inactive
Archivée
```

Ne pas supprimer aveuglément une classe qui pourrait être utilisée par de futurs modules.

Prévoir plutôt :

* désactivation ;
* archivage ;
* suppression uniquement si aucune dépendance importante n'existe.

Préparer la structure pour les futurs modules :

* élèves ;
* inscriptions ;
* enseignants ;
* emploi du temps ;
* évaluations.

# 7. GESTION DES SALLES

Créer une gestion complète des salles.

Une salle doit appartenir à une école et à son tenant.

Prévoir notamment :

* nom ou numéro ;
* code éventuel ;
* capacité ;
* type de salle ;
* statut ;
* école ;
* tenant.

Exemples :

```text
Salle 01
Salle 02
Laboratoire
Salle Informatique
Salle Polyvalente
```

Prévoir des types suffisamment flexibles pour s'adapter aux établissements.

---

# 8. CAPACITÉ DES SALLES

Une salle peut avoir une capacité maximale.

Exemple :

```text
Salle 01
Capacité : 50 élèves
```

Prévoir les validations nécessaires.

La capacité d'une salle ne doit pas être incohérente.

Si une classe possède une capacité maximale, le système doit pouvoir vérifier les incohérences éventuelles.

Ne pas développer encore la gestion des élèves ou des inscriptions.

Préparer uniquement l'architecture nécessaire pour les futures validations.

---

# 9. ASSOCIATION CLASSE / SALLE

Permettre l'association d'une classe à une salle.

Exemple :

```text
6ème Scientifique A
        ↓
Salle 01
```

Vérifier :

* que la classe et la salle appartiennent à la même école ;
* que les deux appartiennent au même tenant ;
* que l'association est cohérente avec l'année scolaire si le modèle le prévoit.

Préparer l'architecture pour les futurs emplois du temps.

Ne pas développer le module complet d'emploi du temps dans cette phase.

---

# 10. GESTION DES CONFLITS

Prévoir une architecture extensible pour les conflits futurs.

Par exemple, une salle pourrait être utilisée par plusieurs classes selon différents horaires.

Ne pas bloquer inutilement cette possibilité.

La gestion complète des conflits horaires sera réalisée dans le futur module d'emploi du temps.

La Phase 2.1 doit uniquement éviter les associations clairement incohérentes.
