# PARTIE D — PHASE 3.1 : INSCRIPTIONS

## 1. OBJECTIF

Créer un système d'inscription permettant d'affecter un élève à une classe pour une année scolaire donnée.

Structure :

```text
Élève
    ↓
Inscription
    ↓
Année scolaire
    ↓
Classe
```

Une inscription doit permettre de connaître :

* quel élève ;
* dans quelle école ;
* pour quelle année scolaire ;
* dans quelle classe ;
* à quelle date ;
* avec quel statut.

---

# 2. MODÈLE D'INSCRIPTION

Créer une architecture cohérente avec les modèles existants.

Une inscription doit être liée à :

* l'élève ;
* l'école ;
* le tenant ;
* l'année scolaire ;
* la classe ;
* éventuellement l'option/filière selon l'architecture existante ;
* la date d'inscription ;
* le statut.

Les relations doivent être validées côté backend.

---

# 3. RÈGLES MÉTIER

Un élève ne doit pas avoir plusieurs inscriptions actives pour la même année scolaire.

Exemple interdit :

```text
Élève A
    ├── 2026-2027 → Classe A
    └── 2026-2027 → Classe B
```

Exemple autorisé :

```text
Élève A
    ├── 2024-2025 → Classe A
    ├── 2025-2026 → Classe B
    └── 2026-2027 → Classe C
```

Un élève peut donc avoir un historique scolaire.

---

# 4. HISTORIQUE DES INSCRIPTIONS

L'architecture doit permettre de conserver l'historique :

```text
Élève
    ↓
2024-2025 → Classe A
2025-2026 → Classe B
2026-2027 → Classe C
```

Ne pas supprimer l'historique d'une ancienne année scolaire simplement parce que l'élève change de classe.

Les anciennes inscriptions doivent pouvoir être :

* consultées ;
* archivées ;
* conservées pour l'historique.

---

# 5. STATUTS D'INSCRIPTION

Prévoir des statuts cohérents.

Par exemple :

```text
En attente
Active
Terminée
Annulée
```

Les statuts doivent être adaptés à l'architecture et aux règles du projet.

Une inscription annulée ne doit pas être considérée comme une inscription active.

---

# 6. CRÉATION D'UNE INSCRIPTION

Prévoir un flux clair :

```text
Créer une inscription
        ↓
Sélectionner un élève
        ↓
Sélectionner une année scolaire
        ↓
Sélectionner une classe
        ↓
Vérifier les relations
        ↓
Valider
        ↓
Créer l'inscription
```

Lors de la sélection de la classe :

* ne montrer que les classes de l'école courante ;
* ne montrer que les classes compatibles avec l'année scolaire ;
* vérifier les relations avec le niveau et l'option ;
* empêcher les associations incohérentes.

---

# 7. RECHERCHE D'UN ÉLÈVE

Lors de la création d'une inscription, permettre de rechercher l'élève par :

* matricule ;
* nom ;
* prénom.

La recherche doit être dynamique.

Ne pas charger inutilement tous les élèves si la base devient importante.

---

# 8. SÉLECTION DE L'ANNÉE SCOLAIRE

Afficher uniquement les années scolaires de l'école courante.

Une année scolaire d'une autre école ne doit jamais pouvoir être utilisée.

Si une année scolaire est inactive, terminée ou archivée, respecter les règles métier définies.

Ne pas permettre une nouvelle inscription dans une année qui ne doit plus accepter d'inscriptions.

---

# 9. SÉLECTION DE LA CLASSE

Afficher uniquement les classes compatibles avec :

* l'école ;
* le tenant ;
* l'année scolaire sélectionnée.

Si la classe est liée à un niveau ou une option, respecter ces relations.

Ne jamais permettre :

```text
Élève de l'École A
        ↓
Classe de l'École B
```

---

# 10. CHANGEMENT DE CLASSE

Prévoir un mécanisme permettant de gérer un changement de classe lorsque cela est nécessaire.

Le système doit conserver l'historique.

Ne pas simplement modifier silencieusement l'ancienne inscription.

Selon les règles métier retenues :

```text
Ancienne inscription
        ↓
Terminée / Historique
        ↓
Nouvelle inscription
        ↓
Nouvelle classe
```

La modification doit être traçable.

---

# 11. LISTE DES INSCRIPTIONS

Créer une page complète avec :

* matricule de l'élève ;
* nom de l'élève ;
* année scolaire ;
* classe ;
* niveau ;
* option/filière si applicable ;
* date ;
* statut.

Prévoir :

* recherche ;
* filtres ;
* consultation ;
* modification selon les règles ;
* changement de statut.

---

# 12. FICHE DÉTAILLÉE DE L'ÉLÈVE

La fiche de l'élève doit permettre de consulter :

```text
Informations personnelles
        ↓
Matricule
        ↓
Parent / Tuteur principal
        ↓
Historique des inscriptions
        ↓
Année actuelle
        ↓
Classe actuelle
```

Ne pas afficher de données provenant d'une autre école.

---

# 13. CAPACITÉ DES CLASSES

Vérifier la capacité de la classe si le modèle existant le permet.

Si une classe possède une capacité maximale :

```text
Capacité maximale : 50
Élèves inscrits : 50
```

Le système doit appliquer la règle métier définie.

Si la classe est pleine :

* empêcher une nouvelle inscription ;
* ou demander une confirmation/autorisation selon les règles de l'application.

Ne pas contourner la capacité silencieusement.

---

# 14. PERMISSIONS

Respecter les permissions existantes.

Un utilisateur ne doit jamais pouvoir :

* inscrire un élève d'une autre école ;
* utiliser une classe d'une autre école ;
* utiliser une année scolaire d'une autre école ;
* consulter les inscriptions d'une autre école ;
* modifier une inscription d'une autre école.

Tester les accès directs aux URLs.

Tester la modification manuelle des identifiants.

---

# 15. ISOLATION MULTI-TENANT

Tester explicitement :

```text
École A ≠ École B
```

Vérifier :

```text
Élève A
    ↓
École A
    ↓
Année A
    ↓
Classe A
```

Ne doit jamais pouvoir être associé à :

```text
Année B
Classe B
École B
```

Toutes les validations doivent être faites côté backend.
